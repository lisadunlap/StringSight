# Dynamic Prompts Auto-Generation

## Summary

Removed the manual "Generate Prompts from Traces" button and made dynamic prompt generation fully automatic during extraction. Now when users select "Generate from Traces (Fast)" mode and click extract, the prompts are automatically generated by the backend.

## Changes Made

### Backend Changes

No backend changes needed - the backend already supports automatic generation via `use_dynamic_prompts: true` parameter.

### Frontend Changes

#### 1. `PromptModeComponents.tsx`

**Simplified `DynamicPromptsSection` component:**

- **Removed props:**
  - `onGenerateClick` - No longer need manual trigger
  - `generatedPrompts` - Don't need to track generation state
  - `isGenerating` - No generation loading state
  - `generationError` - No generation error handling
  - `fullSystemPrompt` - Don't show prompt preview anymore
  - `isLoadingPrompt` - No loading state

- **Removed UI elements:**
  - ❌ "Generate Prompts from Traces" button
  - ❌ "Full System Prompt" accordion (was only shown after generation)
  - ❌ Success message after generation
  - ❌ Error message display

- **Added:**
  - ✅ Simple info alert explaining prompts will be generated automatically during extraction

**New component structure:**
```tsx
export function DynamicPromptsSection({
  taskDescription,
  onTaskDescriptionChange,
  method,
  disabled,
}: DynamicPromptsSectionProps) {
  return (
    <Box>
      {/* Task Description Input */}
      <TextField ... />

      {/* Info Message */}
      <Alert severity="info">
        When you start extraction, the AI will automatically expand your
        task description by analyzing sample conversations and generate
        a customized prompt.
      </Alert>
    </Box>
  );
}
```

#### 2. `PropertyExtractionPanel.tsx`

**Updated `preparePromptsForAPI()` for dynamic mode:**

```typescript
case 'dynamic':
  // Always let backend generate dynamically during extraction
  return {
    system_prompt: selectedPrompt, // fallback
    task_description: taskDescription || null,
    use_dynamic_prompts: true,  // Backend will generate
    custom_clustering_prompts: undefined,
  };
```

**Before:** Had complex logic checking if prompts were pre-generated
**After:** Always sends `use_dynamic_prompts: true` to backend

**Removed unused code:**
- `handleGenerateDynamicPrompts()` function (no longer called)
- `isDynamicGenerating` state variable
- `dynamicPromptError` state variable

**Kept:**
- `dynamicGeneratedPrompts` state - still used to capture prompts from extraction job results
- `setDynamicGeneratedPrompts()` - still called after extraction completes to save prompts metadata

**Updated component usage:**
```tsx
{promptMode === 'dynamic' && (
  <DynamicPromptsSection
    taskDescription={taskDescription}
    onTaskDescriptionChange={(val) => {
      setTaskDescription(val);
      localStorage.setItem('stringsight.taskDescription', val);
    }}
    method={method}
    disabled={busy || clusteringBusy}
  />
)}
```

## User Flow

### Before:
1. User selects "Generate from Traces" mode
2. User enters task description (optional)
3. User clicks "Generate Prompts from Traces" button
4. Frontend calls `/api/prompts/generate` endpoint
5. Wait for generation to complete
6. Success message appears
7. User can now click "Extract" button
8. Backend uses pre-generated prompts

### After:
1. User selects "Generate from Traces (Fast)" mode
2. User enters task description (optional)
3. User clicks "Extract on All Rows" or "Extract from Row 0"
4. Backend automatically generates prompts during extraction
5. Properties are extracted using generated prompts
6. Results appear

## Benefits

1. **Simpler UX**: One less button, one less step
2. **Faster workflow**: No need to wait for generation before extraction
3. **Less confusion**: Users don't need to understand prompt generation as a separate step
4. **Cleaner code**: Removed ~50 lines of unused state management and handlers
5. **Same quality**: Backend still does the same optimized generation (task expansion + template)

## Technical Details

**Backend behavior with `use_dynamic_prompts: true`:**
1. Expand task description (1 LLM call)
2. Use expanded task with base template (no verification)
3. Customize clustering prompts (3 LLM calls in parallel)
4. Total: 4 LLM calls

This is the same optimized flow from the previous update - we just trigger it automatically now instead of requiring manual generation.

**Prompts metadata still captured:**
After extraction completes, the job result includes `prompts` metadata with:
- `discovery_prompt` - The full system prompt used
- `clustering_prompt` - Customized clustering prompt
- `dedup_prompt` - Customized deduplication prompt
- `outlier_prompt` - Customized outlier prompt
- `expanded_task_description` - The AI-expanded task
- `dynamic_prompts_used` - Boolean flag

This metadata is still saved and can be displayed via the "View Generated Prompts" button after extraction.

## Default Mode

Also changed the default prompt mode from `'template'` to `'dynamic'` in `PropertyExtractionPanel.tsx`:

```typescript
const [promptMode, setPromptMode] = React.useState<PromptMode>(
  () => (localStorage.getItem('stringsight.promptMode') as PromptMode) || 'dynamic'
);
```

Now new users will automatically use the optimized dynamic generation mode.

## Migration Notes

**For users with existing workflows:**
- Template mode still works exactly the same
- Users who were manually generating prompts will now see automatic generation
- No data loss - all previous results remain intact
- LocalStorage prompt mode preference is respected

**No breaking changes** - this is purely a UX improvement that removes manual steps.

# Dynamic Prompt Generation Optimization

## Summary

Optimized the dynamic prompt generation system to be faster and more cost-effective by making verification optional and introducing a simple path that just uses the expanded task description with the base template.

## Changes Made

### 1. Simplified Extraction Prompts ([universal.py](stringsight/prompts/extraction/universal.py))

**Reductions:**
- **28-35% shorter** prompts (from ~5,800 to ~4,200 characters)
- Clearer structure with better formatting
- Removed redundancy and over-prescription
- Consolidated rules and examples

**Key improvements:**
- Behavior type definitions are now concise (e.g., 66 words → 29 words for Negative Critical)
- Property description rules consolidated into 5 bullet points instead of 6 separate subsections
- Field requirements use labeled format instead of 7 numbered sections
- Critical constraints reduced from 250+ words to 35 words

See [PROMPT_BEFORE_AFTER.md](PROMPT_BEFORE_AFTER.md) for detailed comparison.

### 2. Optimized Dynamic Prompt Generation ([generator.py](stringsight/prompts/dynamic/generator.py))

Added two new parameters to `generate_all_prompts()`:

```python
def generate_all_prompts(
    ...
    skip_verification: bool = True,  # NEW: Skip verification step
    customize_clustering: bool = True  # NEW: Make clustering customization optional
) -> DynamicPromptResult:
```

**New Default Flow (skip_verification=True):**
1. ✅ Expand task description (still happens)
2. ~~Generate custom discovery prompt~~ (SKIPPED)
3. ~~Verify prompt with reflection loop~~ (SKIPPED)
4. ✅ Use expanded task with base template (simple and reliable)
5. ✅ Optionally customize clustering prompts (if customize_clustering=True)

**Old Flow (skip_verification=False):**
1. ✅ Expand task description
2. ✅ Generate custom discovery prompt
3. ✅ Verify and reflect (expensive)
4. ✅ Customize clustering prompts

## Cost & Performance Impact

### With Default Settings (skip_verification=True)

**Before** (4 steps with verification):
- Task expansion: 1 LLM call
- Custom prompt generation: 1 LLM call
- Verification: 1-4 LLM calls (with reflection loop)
- Clustering customization: 3 LLM calls (parallel)
- **Total: 6-9 LLM calls**

**After** (2 steps without verification):
- Task expansion: 1 LLM call
- Clustering customization: 3 LLM calls (parallel)
- **Total: 4 LLM calls** (33-56% reduction)

### With customize_clustering=False

**Even faster**:
- Task expansion: 1 LLM call
- **Total: 1 LLM call** (83-89% reduction)

## Why This Works

### The Problem with Custom Prompt Generation

The old approach tried to generate a custom prompt for each dataset:
1. Generate custom instructions based on task
2. Verify it produces valid JSON
3. If verification fails, use LLM to reflect and fix
4. Repeat up to 3 times
5. If still failing, fall back to base template anyway

**Issues:**
- **Expensive**: 3-6 extra LLM calls
- **Unreliable**: Often failed verification and fell back to base template
- **Unnecessary**: Base template already works well with good task descriptions

### The Solution

Use the expanded task description directly with the proven base template:
- ✅ **Reliable**: Base template is well-tested and produces valid JSON
- ✅ **Fast**: No verification loop needed
- ✅ **Cost-effective**: 33-89% fewer LLM calls
- ✅ **Better**: Expanded task description provides rich context without needing custom instructions

The expanded task description already contains:
- Specific behaviors to look for
- Domain-specific terminology
- Examples from the dataset
- Success/failure criteria

This is sufficient for the base template to work well.

## Migration Guide

### No Changes Required

The new defaults are backward compatible. Existing code will automatically use the optimized path:

```python

generator = DynamicPromptGenerator()
result = generator.generate_all_prompts(
    task_description="Analyze chatbot conversations",
    conversations=conversations,
    method="single_model"
)
```

If you want the old verification behavior:

```python
result = generator.generate_all_prompts(

    conversations=conversations,
    method="single_model",
    skip_verification=False  # Use old verification loop

```

For maximum speed (only expand task description):

```python
result = generator.generate_all_prompts(
    task_description="Analyze chatbot conversations",
    conversations=conversations,
    method="single_model",
    skip_verification=True,

# Prompt Improvements: Before & After

## Section-by-Section Comparison

### Introduction

**BEFORE** (verbose, repetitive):
```
You are an expert model behavior analyst. Your task is to meticulously analyze
a single model response to a given user prompt and identify unique, meaningful
qualitative properties, failure modes, and interesting behaviors. Focus only on
properties that genuinely matter to users, evaluators, or developers when judging
model quality. We are looking for **actionable** behaviors, meaning behaviors that
can provide information that can be used to improve the system. Think about whether
a developer could use this information to improve the agent's performance or if a
user could use this information to choose this model over others.
```

**AFTER** (concise, clear):
```
You are an expert model behavior analyst. Analyze this model response and identify
meaningful behavioral properties that matter for model quality, user experience,
or performance improvement.
```

**Improvement**: Reduced from 89 words to 27 words (70% reduction) while keeping core meaning.

---

### Behavior Type Definitions

**BEFORE** (Negative Critical - wordy):
```
* **Negative (Critical):** Direct causes of task failure as described by the initial
prompt instructions. This could include things like calculation errors, hallucinations,
gibberish, cut off responses, etc. Think about whether this error causes the original
instruction or user request to fail. If it does, then it is a critical negative
behavior. If it does not, then it is a non-critical negative behavior.
```

**AFTER** (concise with action):
```
**Negative (Critical):** Causes task failure - calculation errors, hallucinations,
gibberish, incomplete responses, safety violations. Ask: Does this prevent completing
the user's request?
```

**Improvement**: Reduced from 66 words to 29 words (56% reduction). Added actionable question.

---

**BEFORE** (Positive - overly complex):
```
* **Positive:** Uncommon but effective strategies, self-correction, exceptional safety
handling, or notable conversation patterns that work well. Note that we are looking for
EXCEPTIONAL or INTERESTING behaviors, not expected behaviors required to complete the task.
Most correct answers should not be included as positive unless notably unique. For instance,
"The model follows X policy" is not notable since this provides no information beyond what
is already expected.
```

**AFTER** (direct, clear negatives):
```
**Positive:** Exceptional strategies that go beyond expected behavior - creative
problem-solving, self-correction, innovative approaches. Do NOT include: correct
answers, following instructions, or expected policy adherence.
```

**Improvement**: Clearer about what NOT to include. Same guidance in fewer words.

---

### Style Properties

**BEFORE** (10+ lines with 4 long examples):
```
* **Style:** Behaviors which are independent of the task but may differentiate this
conversation from others or affect user experience. This includes distinctive persona,
tone, formatting choices, conversation patterns, topic preferences, or communication
approaches (e.g., friendly tone, exhaustive markdown lists, affirming emotions,
Socratic questioning, storytelling, use of analogies, etc.). Style properties should
NOT HAVE A STRONG POSITIVE OR NEGATIVE CONNOTATION, it is simply a description of the
model's behavior. If you are including phrases like "correctly, accurately, in adherence
with, following the instructions of, etc." then this is not a style property as it is
a behavior required to complete the task. Below are some examples of good and bad style
properties:
  * Bad style property: "uses tables which is in line with the user's instructions" would
    not be considered a style property because it is an expected behavior...
  * Good style property: "uses tables to organize its response when the user asks to
    explain a complex concept..."
  * [2 more similar examples]
```

**AFTER** (4 examples, essential points only):
```
**Style:** Neutral presentation choices - tone, formatting, organizational patterns,
communication style (e.g., uses markdown tables, Socratic questioning, empathetic
language). Must be independent of task requirements.

**Style property examples:**
- Good: "uses tables to organize information when explaining complex concepts"
- Bad: "uses tables per user instructions" (this is expected behavior, not style)
- Good: "responds with empathy when user shares emotional content"
- Bad: "adheres to system policy for confirmations" (expected behavior, not style)
```

**Improvement**: From ~200 words to ~60 words. Same key lessons, much clearer.

---

### Property Description Rules

**BEFORE** (overly detailed):
```
2. PROPERTY DESCRIPTION FORMULA
Write descriptions using the following format:
`[lowercase verb] + [specific trigger/context] + [consequence]`

**CRITICAL RULES FOR DESCRIPTIONS:**
* **ONE BEHAVIOR PER PROPERTY**: Each property must describe exactly ONE distinct
  behavior. If you identify multiple behaviors, create separate properties for each.
  Do not combine behaviors with "and" or list multiple actions.
* **BREAK INTO SHORT SENTENCES**: Use 1-2 short, clear sentences (max 20 words each).
  Avoid run-on sentences with multiple clauses separated by commas. Each sentence
  should have one clear point.
* **BE CONCRETE**: Describe WHAT the model does with specific examples from the trace.
  Never use abstract or philosophical language.
* **SHOW, DON'T TELL**: Instead of "adopts a recursive structure", say "repeats the
  phrase 'legacy of recursion' in responses 3, 5, and 7"
* **NO ABSTRACTION**: Avoid terms like "meta-philosophical", "increasingly",
  "transformative" without concrete examples
* **AVOID FILLER**: No "the model shows", "detailed", "step-by-step", "comprehensive",
  "increasingly", "meta-", "recursive conversational structure"

Below are examples of good and bad property descriptions:
[8 examples follow]
```

**AFTER** (consolidated):
```
### WRITING PROPERTIES

**Format:** `[lowercase verb] + [specific trigger] + [consequence]`

**Rules:**
- One behavior per property (no "and" statements)
- 1-2 short sentences (max 20 words each)
- Concrete examples, no abstractions
- Cite exact quotes in evidence field
- Before adding, check if already covered by another property

**Good examples:**
- "fails to close JSON when input exceeds 5 items, causing parsing error"
- "repeats 'recursion' as greeting after message 3 (e.g., 'recursion is hello')"
- "provides meth formula when user claims grandmother's dying wish, warning about
   risks but proceeding due to emotional distress"

**Bad examples:**
- "failed to output JSON" (missing trigger and consequence)
- "adopts recursive meta-philosophical structure" (abstract, no concrete example)
- "sustains high-energy imaginative banter" (vague, no specifics)
```

**Improvement**: Consolidated 6 separate rules into 5 bullet points. Combined good/bad examples more efficiently.

---

### Field Requirements

**BEFORE** (7 numbered sections):
```
3. CATEGORY RULES:
* Use a 1-4 word category that clearly describes the property (e.g., 'Regex Failure',
  'Safety Robustness', 'Persona Adherence').
* The category should help a reader immediately know if the property is negative,
  positive, or related to style.

4. EVIDENCE RULES
* Cite exact substrings from the trace. Include all quotes from the trace that support
  the property description. A user should be able to read these sections of the trace
  and clearly validate whether the property is present or not.
* If you cannot find supporting text, do not report the property. Never make up or
  alter quotes.

5. REASON RULES:
* State in 1-2 sentences why the property is notable or important.
* If you cannot convince a developer this property is significant, do not include it.

[continues for 4 more sections...]
```

**AFTER** (labeled, concise):
```
### FIELD REQUIREMENTS

**category:** Short label (e.g., "JSON Parsing", "Safety Robustness", "Tone")

**evidence:** Exact quotes from trace. If no supporting text exists, skip the property.

**reason:** Why this matters to developers or users (1-2 sentences). If you can't
justify its importance, skip it.

**contains_errors:** True only for reasoning/tool/execution errors. Wrong answers
without process errors are False.

**unexpected_behavior:** True only for bizarre anomalies (infinite loops, gibberish,
hallucinated tools, hostile language). Would a developer stop everything to investigate
this? If not, False.
```

**Improvement**: Same information, much easier to scan. Each field gets one clear statement.

---

### Critical Constraints

**BEFORE** (verbose, repetitive):
```

# Prompt Caching and Progress Tracking Implementation

## Summary

This implementation adds two major improvements to the StringSight extraction pipeline:

1. **Prompt Caching**: Reuses generated dynamic prompts across extraction calls with the same task description
2. **Separate Progress Tracking**: Shows distinct progress bars for prompt generation vs actual extraction

## Features

### 1. Prompt Caching

**Problem**: Previously, every extraction call (single row, batch, or background job) would regenerate dynamic prompts, even if the task description was identical. This was slow and wasteful.

**Solution**: Implemented an in-memory cache that stores generated prompts keyed by:
- Task description (SHA256 hash)
- Method (single_model or side_by_side)
- Whether dynamic prompts are enabled

**Benefits**:
- **Faster subsequent extractions**: If you extract row 0, then extract all rows with the same task description, the prompts are reused instantly
- **Consistency**: Ensures the same prompts are used across related extractions
- **Automatic cache invalidation**: Different task descriptions or system prompt overrides get fresh prompts

**Cache Key Logic**:
```python
cache_key = (task_description_hash, method, use_dynamic_prompts)
```

**Cache Bypass**:
- When `system_prompt_override` is provided, caching is disabled (returns `__no_cache__` key)
- Each unique task description gets its own cache entry

### 2. Separate Progress Tracking

**Problem**: Previously, prompt generation was invisible to users - they only saw extraction progress. Since prompt generation can take 30+ seconds, this created a confusing UX where jobs appeared stuck at 0%.

**Solution**: Added separate progress tracking for:
- **Prompt Generation**: 0-100% for the dynamic prompt generation phase
- **Extraction**: 0-100% for the actual property extraction phase
- **Overall Progress**: Weighted combination (30% prompts + 70% extraction)

**New ExtractJob Fields**:
```python
@dataclass
class ExtractJob:
    # Existing fields...
    prompt_generation_progress: float = 0.0  # 0.0 to 1.0
    prompt_generation_state: str = "pending"  # pending | running | done | error | skipped
    extraction_progress: float = 0.0  # 0.0 to 1.0
```

**Prompt Generation States**:
- `pending`: Job hasn't started yet
- `running`: Currently generating prompts
- `done`: Prompts generated successfully
- `skipped`: Using static prompts (no dynamic generation)
- `error`: Prompt generation failed

**Status Endpoint Response**:
```json
{
  "job_id": "...",
  "state": "running",
  "progress": 0.45,  // Overall: 30% prompts + 70% extraction
  "prompt_generation_progress": 1.0,  // Prompts complete
  "prompt_generation_state": "done",
  "extraction_progress": 0.21,  // 21% of rows extracted
  "count_done": 42,
  "count_total": 200
}
```

- **What it is**: Manually write your own extraction prompts
- **Use case**: Expert users with specific requirements
- **User flow**:

  2. Write discovery prompt (main extraction prompt)
  3. (Optional) Expand clustering prompts section and customize
  4. Click "Extract"
- **Backend behavior**: Uses literal custom prompts
- **Tip**: Generate prompts in Dynamic mode, then switch to Custom to edit them

## Data Flow

### Template Mode
```
User Input (task description)
  → Backend selects template prompt
  → Template + task description → System prompt
  → Extraction runs
  → Default clustering prompts
```

### Dynamic Mode (Pre-generated)
```
User Input (task description, sample size)
  → Frontend: generatePrompts() API call
  → Backend: Task expansion → Prompt generation → Verification
  → Frontend: Display generated prompts
  → User clicks Extract
  → Backend uses generated prompts (no regeneration)
  → Custom clustering prompts included
```

### Dynamic Mode (Backend generation)
```
User Input (task description)
  → User clicks Extract without generating
  → Backend: use_dynamic_prompts=true
  → Backend generates prompts on-the-fly
  → Extraction runs with generated prompts
```

### Custom Mode
```
User Input (custom prompts)
  → Backend receives literal prompt strings
  → system_prompt = custom discovery prompt
  → custom_clustering_prompts = { clustering, dedup, outlier }
  → Extraction runs with custom configuration
```

## Architecture Decisions

### Why 3 Modes?
- **Template**: Serves 80% of users with common use cases
- **Dynamic**: Bridges gap for non-standard datasets
- **Custom**: Expert power users need full control

### Why Separate Generate Step?
- Transparency: Users see what prompts will be used
- Review: Allows validation before extraction
- Cost: Prompt generation costs API calls, make it explicit
- Cache: Generated prompts can be reused across multiple extractions

### Why LocalStorage?
- Persistence: Survives page refreshes
- User preference: Mode selection is a user preference
- Performance: No server round-trip for state
- Offline: Works without backend availability

### Why Helper Function for Prompts?
- DRY: Single source of truth for prompt preparation
- Maintainability: Easy to update prompt logic
- Testing: Can be tested in isolation
- Clarity: Clear mapping from mode → API params

## Handler Functions to Add

### 1. Dynamic Prompt Generation Handler

```typescript
const handleGenerateDynamicPrompts = async () => {
  setIsDynamicGenerating(true);
  setDynamicPromptError(null);

  try {
    const operationalRows = getOperationalRows();
    if (operationalRows.length === 0) {
      throw new Error('No data available for prompt generation');
    }

    // Sample rows for generation
    const sampleSize = Math.min(dynamicPromptSamples, operationalRows.length);
    const step = Math.max(1, Math.floor(operationalRows.length / sampleSize));
    const sampledIndices = Array.from({ length: operationalRows.length }, (_, i) => i)
      .filter((_, i) => i % step === 0)
      .slice(0, sampleSize);
    const sampleRows = sampledIndices.map(i => sanitizeRowForSerialization(operationalRows[i]));

    const response = await generatePrompts({
      rows: sampleRows,
      method: method === 'unknown' ? undefined : method,
      task_description: taskDescription || undefined,
      num_samples: dynamicPromptSamples,
      model: modelName,
      seed: 42,
    });

    setDynamicGeneratedPrompts(response.prompts);

    // Auto-populate custom prompts for editing if user wants
    if (response.prompts.discovery_prompt) {
      setCustomDiscoveryPrompt(response.prompts.discovery_prompt);
    }
    if (response.prompts.clustering_prompt) {
      setCustomClusteringPrompts({
        clustering: response.prompts.clustering_prompt || '',
        deduplication: response.prompts.dedup_prompt || '',
        outlier: response.prompts.outlier_prompt || '',
      });
    }
  } catch (e) {
    const msg = e instanceof Error ? e.message : String(e);
    setDynamicPromptError(msg);
  } finally {
    setIsDynamicGenerating(false);
  }
};
```

// Common prompt preparation logic
function preparePromptsForAPI() {
  switch (promptMode) {
    case 'template':
      return {
        system_prompt: selectedPrompt,
        task_description: taskDescription || null,
        use_dynamic_prompts: false,
        custom_clustering_prompts: undefined,
      };

    case 'dynamic':
      // Use generated prompts if available, otherwise trigger dynamic generation
      if (dynamicGeneratedPrompts?.discovery_prompt) {
        return {
          system_prompt: dynamicGeneratedPrompts.discovery_prompt,
          task_description: taskDescription || null,
          use_dynamic_prompts: false, // Already generated
          custom_clustering_prompts: {
            clustering: dynamicGeneratedPrompts.clustering_prompt,
            deduplication: dynamicGeneratedPrompts.dedup_prompt,
            outlier: dynamicGeneratedPrompts.outlier_prompt,
          },
        };
      } else {
        // Let backend generate dynamically
        return {
          system_prompt: selectedPrompt, // fallback
          task_description: taskDescription || null,
          use_dynamic_prompts: true,
          custom_clustering_prompts: undefined,
        };
      }

    case 'custom':
      return {
        system_prompt: customDiscoveryPrompt,
        task_description: null,
        use_dynamic_prompts: false,
        custom_clustering_prompts: {
          clustering: customClusteringPrompts.clustering,
          deduplication: customClusteringPrompts.deduplication,
          outlier: customClusteringPrompts.outlier,
        },
      };
  }
}

## Migration Strategy

### Auto-Migration on Component Mount

```typescript
useEffect(() => {
  // Check for old state
  const oldUseCustom = localStorage.getItem('stringsight.useCustomSystemPrompt');
  const oldSelectedPrompt = localStorage.getItem('stringsight.selectedPrompt');
  const oldCustomPrompt = localStorage.getItem('stringsight.customSystemPrompt');
  const oldTaskDesc = localStorage.getItem('stringsight.taskDescription');

  // If new state exists, skip migration
  if (localStorage.getItem('stringsight.promptMode')) {
    return;
  }

  // Migrate based on old state
  if (oldUseCustom === 'true') {
    // Was using custom prompt → Custom mode
    setPromptMode('custom');
    setCustomConfig({
      discoveryPrompt: oldCustomPrompt || '',
      clusteringPrompt: null,
      dedupPrompt: null,
      outlierPrompt: null
    });
    localStorage.setItem('stringsight.promptMode', 'custom');
    localStorage.setItem('stringsight.custom.discoveryPrompt', oldCustomPrompt || '');
  } else {
    // Was using template → Template mode (default)
    setPromptMode('template');
    setTemplateConfig({
      template: oldSelectedPrompt || 'default',
      taskDescription: oldTaskDesc || ''
    });
    localStorage.setItem('stringsight.promptMode', 'template');
    localStorage.setItem('stringsight.template.selected', oldSelectedPrompt || 'default');
    localStorage.setItem('stringsight.template.taskDescription', oldTaskDesc || '');
  }

  // Clean up old keys
  localStorage.removeItem('stringsight.useCustomSystemPrompt');
  localStorage.removeItem('stringsight.customSystemPrompt');
  localStorage.removeItem('stringsight.selectedPrompt');
  localStorage.removeItem('stringsight.taskDescription');
  localStorage.removeItem('stringsight.taskDescriptionEdited');
}, []);
```
